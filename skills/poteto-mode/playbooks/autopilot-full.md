### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until independent verifiers in your native `/swarm`, who never wrote the code, have proven the code that lands.**

A verdict covers one patch and green CI covers one head. Step 4 runs full verification once, and again only for a major change. The patch-id rule in `playbooks/shipping.md` can carry a lane's result, and every new head needs its own green CI.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
2. **Spawn one owner per PR in native `/swarm`, each in its own shared workspace.** Use GitHub CLI (`gh`) for every PR operation. Name the swarm (`swarm{action:"title", title:"autopilot: <queue>"}`), include the built-in `monitor` if available for stall detection, and add one owner worker per PR with `swarm{action:"add", name:"pr-<slug>", workspace:"share", brief:...}`. Each owner builds, opens its PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact, babysits to green per `playbooks/babysit.md`, and merges once steps 4 and 5 clear it. Where that playbook says to report a rebase, the owner rebases its own branch and publishes it with `git push --force-with-lease`.

   Open the PR early so CI and review bots run alongside the work. The code is ready only after running `unslop` and `/no-comments`, so verification runs on finished code. Then rebase onto current trunk and report the code-ready head on the board before self-proof, so verification runs on the base the patch lands on. Report every later head, and `merge-ready` once self-proof, CI, and babysit are done. Fix rounds stay on that base unless trunk conflicts, breaks CI, or lands a known concurrent change to the same files, because each rebase restarts CI. Run the repo's checks for the touched paths on the committed head before the code-ready push and before a later push that needs a verifier.

   Assume any worker can be killed or restarted. Soon after starting, push and log a decision trail row per the **show-me-your-work** skill, then push each finished unit before starting the next. Force-push only your own branch, with `--force-with-lease` pinned to the SHA you last pushed or took over, and on any push you did not make, stop and report to `@coordinator`.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own.
4. **Swarm-verify once.** Full verification runs once, at the code-ready head. Another full pass runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head, and a wording-only change gets none. Add independent verifier workers on the `/swarm` board (`workspace: "inherit"` or `"share"` when checking out the PR head) that never wrote the code. They re-run the gates, prove the load-bearing behavior live on the real surface (project `verify-*` skill, Antigravity's `browser` subagent, `cua-driver`, or CLI/PTY harness), and audit the diff. The verdict is not clean without the live lane, or before you audit the merge-ready report's receipts, because no lane trusts a claim it has not checked.

   Block a PR only for a problem you can show, with a failing run at the head or a doc line the PR made wrong. A problem the PR's base already has, whether trunk or the PR below it in a stack, doesn't block unless the PR copies it or newly reaches it. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks, and everything else goes in a follow-up.
5. **The owner merges only what you verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. Once verification starts, merge prep rebases onto current trunk, reports the new head, and waits for green CI.

   Right before merging, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install (`bun install --frozen-lockfile` or the repo's frozen install) passes on the merge result and the packages the PR changes resolve there as on the head; a failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If trunk would force a third rebase past merge prep, hold and report to `@coordinator`, which sequences the colliding work.
6. **Run the coordinator layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the owner's record of it points at your countersign for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, set a recurring `schedule` heartbeat (e.g., `CronExpression: "0 * * * *"` or `DurationSeconds: 3600`) alongside the swarm `monitor` until no delegated work is left, because long runs drift and workers stall silently. Each tick re-reads this playbook from trunk, checks `swarm{action:"status"}`, and judges every worker by its side effects (commits, pushes, trail rows), not status prose. Replace a stuck or looping worker cleanly (`kill` only after confirming its pushed branch is safe, then `add` a fresh replacement). If a worker runs out of quota, switch its model with `swarm{action:"model"}` instead of killing it. A tick that changed something for the operator ends by catching them up per the **ketchup** skill, and one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** Post `@all [hold] zero writes — report current state` on the swarm board. Each owner reports where it stands and keeps its brief until the operator releases it. When the whole queue finishes, post `[done] <summary>` (no `@`) and cancel any active `schedule` timers.

**Reply:** catch the operator up per the **ketchup** skill, covering each PR's state and verdict, what merged, countersigns and why, open operator gates, and parked follow-ups, with links to each PR and the trails.
